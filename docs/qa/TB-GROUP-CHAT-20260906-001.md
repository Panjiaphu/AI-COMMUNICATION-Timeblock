## 3. Current problem confirmed in source

Current Group Chat translation is recipient-scoped:

```text
GroupChatTranslation
  recipient_membership_id
  message_id
  target_language
  message_fingerprint
```

Current uniqueness includes recipient identity, and the service looks up translations by recipient. Therefore two members with the same target language can create separate translation records/provider work for the same message version.

Target architecture:

```text
ONE message-version + target-language variant
-> shared by every authorized member with that target language
```

## 4. Canonical Group Chat identity

For editable chat messages, shared variant identity is:

```text
(message_id, message_fingerprint, target_language)
```

`recipient_membership_id` must not be part of the shared translation identity.

If the message is edited:

```text
message_fingerprint changes
-> old variants become stale for current message version
-> old translated text must not be projected as current
-> new target variants are created only when required
```

## 5. Cost ownership

For every Group Chat message:

```text
COST_OWNER=SOURCE_MESSAGE_AUTHOR
```

A recipient can request a missing historical target variant, but:

```text
REQUESTED_BY=recipient
COST_OWNER=original message author
```

Do not silently charge the requester for another member's historical message.

If an existing FINAL variant exists:

```text
provider work=0
additional translation quota/cost=0
```

If a new provider translation is required and the author cannot authorize/pay applicable translation quota:

```text
reuse existing FINAL variant if present
otherwise return truthful quota/unavailable state
```

No fallback requester billing without a new owner decision.

## 6. Realtime Group Chat behavior

For a new eligible text message:

```text
resolve source_language
-> determine UNIQUE required target languages among currently eligible/active recipients
-> remove source_language
-> create/check one shared variant per unique target language
-> one provider call per missing target language
-> all same-language recipients reuse same result
```

Example:

```text
A=vi
B,C=zh-TW
D,E=en

A sends VI message
EXPECTED:
vi source = no translation call
zh-TW variant = one provider call
EN variant = one provider call
TOTAL_PROVIDER_TRANSLATION_CALLS=2
```

Recipient count must not multiply provider translation work.

## 7. Historical Group Chat behavior

History is source-first and on-demand to minimize cost.

Required:

```text
LOAD_SOURCE_HISTORY=YES
LATE_JOIN_HISTORY_AUTO_TRANSLATE=NO
LATE_JOIN_HISTORY_AUTO_READ=NO
HISTORY_TRANSLATE=ON_DEMAND
HISTORY_TTS=MANUAL_ON_DEMAND
```

For each historical message:

```text
if recipient target == source language:
  source text is already usable
else if shared FINAL target variant exists:
  show/reuse it without provider call
else:
  show explicit Translate action
```

When user presses Translate:

```text
check shared variant first
-> FINAL exists: return immediately
-> missing: create shared variant once
-> concurrent identical requests coalesce
```

Manual historical Translate must not trigger Auto Read automatically.

Historical Play is manual and local-device only.

## 8. Concurrency / idempotency requirement

Two users with the same target language can press Translate simultaneously.

Required:

```text
message X + fingerprint F + zh-TW
request by B
request by C

EXPECTED:
provider calls=1
stored shared variants=1
both clients receive same result
```

The implementation must prevent duplicate provider calls, not only duplicate database rows.

Use a stable provider idempotency key derived from message-version + target language.

## 10. Projection / authorization

Shared storage does not mean public access.

Every read/translate action still requires:

- active Group membership;
- current Group translation permission/scope;
- applicable consent/profile rules;
- message still active/current;
- message fingerprint still matches current message revision.

Response projection is recipient-specific even though stored translated text is shared.

Do not expose another room/member's data through shared cache keys.
